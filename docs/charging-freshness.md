# Charging-data freshness in Home Assistant

An unchanged value can still be a new reading. For example, the car can report the same charge level and power for several minutes while charging normally.

Home Assistant's ESPHome integration can discard identical native API states before writing the entity state. In that case, even `last_reported` does not advance. See the [HA Core `2026.10.2` update handler](https://github.com/home-assistant/core/blob/2026.10.2/homeassistant/components/esphome/entry_data.py#L449-L475). `last_changed` and `last_updated` are not receipt timestamps either. A controller that uses these times as a freshness watchdog can stop a healthy charging session.

The general `Last update` sensor cannot prove charging-data freshness: drive, climate, closures, and tyre responses can also update it. BLE signal strength only establishes a radio observation.

## Enable receipt timestamps

Add `packages/charging-freshness.yml` after `packages/common.yml` and `packages/client.yml` in the example configuration's remote package list, then rebuild and install the firmware:

```yaml
packages:
  remote_package_files:
    url: https://github.com/PedroKTFC/esphome-tesla-ble/
    files:
      - packages/base.yml
      - packages/common.yml
      - packages/project.yml
      - packages/client.yml
      - packages/charging-freshness.yml
```

This optional package adds three diagnostic timestamp entities:

| Timestamp | Source reading |
| --- | --- |
| `Charge level received` | `charge_state` (battery percentage) |
| `Charge power received` | `charge_power` |
| `Charging state received` | `charging_state` (such as `Charging` or `Stopped`) |

Each timestamp comes from that field's `on_raw_value` callback and uses the bridge's UTC clock, synchronized by `homeassistant_time` in `common.yml`. Repeated values advance the timestamp. A response that omits one field does not refresh that field's timestamp. Climate and other unrelated responses do not refresh any of these timestamps.

These are bridge receipt times, not timestamps generated by the vehicle. They do not establish the age of data cached inside the vehicle. Resolution is one second; reports within the same second share a timestamp.

No timer republishes the timestamps, and the package does not restore them after a bridge reboot. An API reconnect can replay the last timestamp but cannot make its value newer. Until the clock is valid and a valid sample arrives, a timestamp is unknown or unavailable. Invalid numeric values and unknown charging states publish `unavailable`; the component's disconnect invalidation does the same.

Raw callbacks run before user filters. The package accepts the component's raw English charging states, including `No Power` and `Calibrating`; downstream text translations do not change that check. If a filter delays or suppresses readings, the timestamp describes the raw input, not the filtered output. Freshness-sensitive controls should use unfiltered readings or account for those filters explicitly.

The package does not change polling, wake behavior, charge commands, existing entity names, or `force_update` defaults. Timestamp entities add updates while the car reports data, so they also add recorder activity unless excluded from recording.

## Use the timestamp value

Check the timestamp's **state value**, not its Home Assistant `last_changed`, `last_updated`, or `last_reported` metadata. For example, replace the example entity ID below with the actual entity created for your device:

```jinja
{% set received = as_timestamp(states('sensor.tesla_ble_charge_level_received'), 0) %}
{{ received > 0 and 0 <= as_timestamp(now()) - received <= 180 }}
```

`180` seconds is an example, not a recommended universal timeout. Choose a limit that accounts for the configured polling intervals and transport delays. Apply the check separately to each input used by the controller, and also validate each input's value and availability. A recent timestamp does not mean the car should charge or that a command succeeded. Reject future timestamps as well as missing or expired ones.

Setting `force_update: true` on an individual numeric sensor is an alternative when you specifically need its HA report time to advance for repeated values. Text sensors have no equivalent option. The separate timestamps also preserve the original bridge receipt time when HA receives cached states again.

## Verification

`python -m unittest discover -s tests -v` requires PyYAML and a C++17 compiler. It checks the raw callback wiring and absence of periodic refresh, then compiles and runs the package's actual timestamp lambdas with a controllable clock. It covers repeated readings, numeric bounds, non-finite values, supported and unknown charging states, and an unsynchronized clock.

`esphome compile tests/charging-freshness.yml` builds a dummy ESP32 configuration against the local component and packages. Do not flash that fixture to a real device.

After installing your own configuration, keep the car awake and observe unchanged readings across multiple polls. Their receipt timestamps should advance. Check a quiet or disconnected period and an HA reconnect: the timestamp values must not advance without new raw samples. These checks require hardware; the clock stand-in and firmware compilation do not prove BLE delivery or charging behavior.
